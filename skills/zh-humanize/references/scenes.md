# 情境與改寫力度

> **這整份檔是本專案自寫的，上游沒有對應內容。** 上游的五個情境是電子報 / 社群貼文 / 銷售頁 / 客服回信 / 辦公文書，那是內容創作者的日常；本專案的使用者是拿 bstack 去開發專案的人，日常是 README 與 release notes。
>
> **可信度與 `patterns.md` 不同**：那份有 42 條 benchmark 背書，這份沒有——`evals/benchmark.md` 的用例文本全是上游情境，量不到這份的力度判定。改動這份時沒有回歸網可接。

## 力度尺

**力度只有三檔：輕 / 中 / 重。** 沒有「中偏重」這種檔位——判不出來就取輕的那一檔。

| 檔 | 意思 |
|---|---|
| 輕 | 只砍最明顯的套話開場與結尾，句子結構不動 |
| 中 | 砍空話與避險墊片，可以併句、拆句、重排段內順序 |
| 重 | 可以整句刪除、整段重寫。**目前五個情境都沒有用到這一檔**，保留給日後 |

## 五個情境

| 情境 | 力度 | 禁改項 |
|---|---|---|
| README | 中 | 第一段的類別名詞、安裝指令、版本需求、badge 與連結 |
| release notes | 輕 | 版本號、行為描述、破壞性變更的措辭、issue / PR 編號 |
| 使用文件 | 中 | 步驟順序、指令、參數名、預期輸出 |
| issue 與 PR 回覆 | 中 | 責任歸屬、條件語氣、引用的原話、@ 提及 |
| 產品站文案 | 中 | 數字、連結、CTA 文字 |

### 為什麼 release notes 是輕

它的讀者是來確認「我升級會不會壞」的。**行為描述的每一個限定詞都是資訊**——「多數情況下會自動遷移」不能改成「會自動遷移」，那兩句話對讀者的意義完全不同。這個情境的空話密度本來就低，改寫的收益小、改壞的代價大。

### 為什麼產品站文案不是重

改版面、換文體是**另一件事**，見下方邊界。這裡只砍 AI 味。

## 混合情境

一份檔同時命中兩列時（很常見，下面三組尤其常撞），**取最輕的力度、取兩者禁改項的聯集**。

| 常撞的組合 | 為什麼會撞 |
|---|---|
| README × 使用文件 | 小專案的 README 就是使用文件 |
| README × 產品站文案 | 產品站 hero 常直接抄 README 首段 |
| issue 回覆 × release notes | 在 issue 裡貼變更說明 |

取聯集而不是取交集的理由：**禁改項漏一項的代價，遠大於少改幾句套話的代價。** 保護清單漏掉會改壞事實；力度取輕只是少改一點。

**判不出屬於哪一個情境時**：問使用者一句「這段文字讀者會在哪裡看到？」，不要猜。

## 邊界：文體選擇不歸本 skill 管

**文體選擇不歸本 skill 管。**

具體來說，下面這些**不是**本 skill 的職責：

- 這頁該用開源工具站的寫法（第一行給類別名詞、產品名當主詞）還是 B2B 轉化頁的寫法（benefit headline、大量「你」）
- 段落結構、標題句型、資訊順序
- 該不該加一個 section、該不該砍一個 section

本 skill 只做一件事：**把 AI 味拿掉，其他不動。** 一份文體選錯的文案，去完 AI 味之後仍然是文體選錯的——那要靠別的東西處理，不是這裡。

把這條寫進來，是因為「潤稿」這個詞在使用者心裡通常包含文體調整，而本 skill 不做。**說清楚邊界，比事後解釋為什麼沒做便宜。**
