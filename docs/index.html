攔截

有些事，它不是被勸阻，
是被擋下來

兩個 PreToolUse hook 直接長在工具呼叫的前面，不是寫在 prompt 裡等它自己記得。

branch-safety.ps1 在 project repo 內、當前 branch 命中 main / master / production / prod / release 時擋掉寫入。file-type-guard.ps1 按副檔名與路徑分兩級：密鑰類（.env、*.key、*.pem、credentials.*）直接擋、沒有放行管道；敏感類（migration、lockfile、CI、infra）也擋，但你確認過之後可以建一張一次性 token 放行。至於「migration 要載 db-access」「CI 檔要升到 T2」那些，是攔下來之後 CLAUDE.md 要求它做的處置。hook 只負責讓那個動作沒有發生過。

原本靠它自律

規則寫在 prompt 裡。多數時候它會遵守，偶爾在一長串工具呼叫之後忘記，然後你在 git log 裡看到一個直接打在 main 上的 commit。

現在擋在工具前面

hook 先跑。命中就 exit 2，工具呼叫直接失敗、那個動作沒有發生過，stderr 同時告訴它「去開一支 branch 再回來」。

判定

先估這件事有多大，
再決定要多認真

一行 typo 跟改動資料庫結構，不該用同一套程序處理。

每個請求進來先跑 Phase 0：讀 memory、看 codebase、估影響檔、判是修 bug 還是做功能、判量體落在 T0 到 T3 哪一級。判完把三件事併成一張選單問你，只能點選項，沒有自由填答欄。

原本每次不一樣

同一句「改一下這裡」，它今天直接動手，明天先寫一份規格再問你三個問題。你沒辦法預期這次會拿到什麼。

現在先估量體再分流

T0 一行改動直接做完，T3 跨模組或動到 DB schema 要走完九個階段。「好」「OK」這種字一律不算通過，gate 只認選項。

設計

動前端檔之前，
先讀這一區原本長什麼樣

改樣式很少壞在寫錯字。壞的是憑印象重畫，然後把前台的顏色套到後台。

碰到前端檔會先查這塊屬於哪一套設計語言、把實際的色碼與字級抄出來，抽不到就說抽不到。沿用既有 token 的小改直接做完再對四項檢查；新頁或改版屬於大改，會先出三個差異化方向、附真實視覺讓你挑，選定才落 code。

原本憑印象重畫

「顏色我記得是那個藍」。做出來的東西單看沒問題，跟旁邊的畫面擺在一起就是不對，但說不出哪裡不對。

現在從實際檔案抄值

色碼、字級、圓角、斷點全部照抄並記下來源檔與行號。抽不到就說抽不到，不拿別區的值頂替。

規劃

大改動要先把計畫
拆給四個人看

判到 T3 時，它不會直接開始寫，會先把需求寫成規格、再拆成一條條可執行的 task。

計畫寫完派四個視角各看一遍：策略上該不該現在做、介面上會不會難用、架構上失敗了怎麼回退、接手的人讀不讀得懂。四份意見整合完、你點頭了才進實作。

原本邊寫邊想

直接開始改，改到一半發現方向錯了，前面兩小時的產出跟著作廢——而且通常是在快寫完的時候才發現。

現在計畫先被打槍

task 拆得夠細，每條都標好要動哪些檔、能不能跟別條平行跑。計畫被打槍的成本，遠低於實作被打槍。

施工

先寫會失敗的測試，
再寫讓它過的 code

每個 task 都走同一組五步，中間不許跳。

寫測試 → 跑到它紅 → 寫最小實作 → 跑到它綠 → commit。途中如果冒出計畫裡沒寫到的前端檔，它會停下來重新判定該區塊的設計語言，不會順手改一改當作沒發生過。

原本一次改一大包

一輪對話改了七個檔、湊成一個 commit，訊息寫「fix issues」。三個月後有人想知道其中一行為什麼那樣寫，沒有人答得出來。

現在一個 commit 一件事

訊息用繁中寫清楚改了什麼、為什麼改，不寫怎麼做。怎麼做看 diff 就有。

審查

審查的人
不知道你為什麼那樣寫

review、安全稽核、e2e、假設驗證全部派給獨立 context 的 subagent。

六個 agent 各有專責：lang-reviewer 依改的檔自動派發、按語言抓對應的 idiom 與 pitfall；security-auditor 跑 OWASP 與 STRIDE；db-reviewer 看 schema 與 migration；frontend-e2e-runner 把 browser 那一大堆 log 隔在自己的 context 裡。

原本自己審自己

同一段對話裡請它檢查剛才寫的 code。它知道每一行當初為什麼那樣寫，於是每一行看起來都很合理。

現在換一個沒有記憶的人看

agent 在獨立 context 裡只拿得到成品，看不到實作過程。寫的人記得為什麼，讀的人不記得。過得了這一關，才算真的寫清楚了。

留痕

每一輪結尾
都告訴你它站在哪

回覆的最後一行永遠是一條 Trace：現在在哪個階段、判定是哪一級、走的是修 bug 還是做功能。

PR 開完之後還有一個 agent 重讀一次 diff，寫成「為什麼改、怎麼做、跟哪裡有關」三層說明，落成獨立檔案再貼回 PR。它刻意不知道實作過程。

原本往回翻對話

想知道它為什麼做了某個決定，只能往上捲，在幾十輪對話裡找那句話。

現在每輪都留一行

[Trace] Phase=execute-plan | Tier=T2 | Track=Dev | Skill=execute-plan：phase 透明，想查哪一輪都翻得到。

裝進 ~/.claude/ 的全部

  • skills主流程 12 條、跨流程觸發式 9 條、meta 4 條、設計 lane 2 條27
  • agentsreview / 安全稽核 / e2e / 假設驗證，各自跑獨立 context6

Dev track 的九個階段

Bug track 走 debug-systematic 取代第 2、3 階段，其餘相同。Tier 決定哪幾階段被跳過。

  • 01brainstorm
  • 02write-plan
  • 03execute-plan
  • 04verify-done
  • 05request-review
  • 06security-audit
  • 07finish-branch
  • 08pr-explain
  • 09retro

裝起來要四步

需要 git、jq、Node.js 與 npx。mysql MCP 的連線目標可選。

  1. 取得 repo
    git clone https://github.com/fujiei22/bstack.git
cd bstack
  2. 同步到 ~/.claude/

    檔案直接覆蓋、不備份，先自己備份再跑。settings.json 走 merge：hooks 與 statusLine 以 repo 為準，permissions.* 與其他設定一律保留本機既有值。

    pwsh -File scripts/setup.ps1
  3. 裝兩個 MCP

    mysql MCP 的三個寫入開關都設 false，並建議搭配唯讀權限的 DB user 做雙保險。

    claude mcp add mysql --scope user --env ALLOW_INSERT_OPERATION=false …
claude mcp add playwright --scope user -- npx -y @playwright/mcp@latest
  4. 開新 session

    既有的 Claude Code session 不會載入新裝的 skill，要開新的才生效。
